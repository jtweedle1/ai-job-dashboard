<objective>
Create the server-side auth infrastructure (lib/auth-server.ts) and update all 7 API routes to verify a Firebase ID token from the Authorization header instead of trusting a client-supplied uid.

Purpose: This is the highest-severity vulnerability. Any caller who knows a Firebase UID can currently read encrypted API keys, trigger AI calls on the victim's Anthropic quota, and write data to their account. After this plan, uid is always derived server-side from a cryptographically verified token.

Output: lib/auth-server.ts (new), 7 updated route.ts files (uid no longer accepted from body/query).
</objective>

Create lib/auth-server.ts (new file, server-only — no "use client" directive).

Import getAuth from "firebase-admin/auth" and the existing firebase-admin app initialisation indirectly by importing adminDb from "@/lib/firebase-admin" (this import guarantees the Admin app is initialised before getAuth() is called).

Export a single async function:

  export async function requireAuth(request: Request): Promise<{ uid: string }>

Implementation:
1. Read the Authorization header from request.headers.get("Authorization").
2. If missing or does not start with "Bearer ", return NextResponse.json({ error: "unauthorized" }, { status: 401 }).
3. Extract the token: the substring after "Bearer " (trimmed).
4. Call const decoded = await getAuth().verifyIdToken(token). Wrap in try/catch — if verifyIdToken throws (expired, revoked, malformed), return the same NextResponse 401 from step 2.
5. Return { uid: decoded.uid }.

The function NEVER throws — it always returns either a NextResponse (on auth failure) or { uid: string } (on success). This is the return-based pattern; do NOT use throw here.

Return type:

  export async function requireAuth(request: Request): Promise<NextResponse | { uid: string }>

Provide a usage pattern comment at the top of the file:

  // Usage in route handlers:
  // const authResult = await requireAuth(request);
  // if (authResult instanceof NextResponse) return authResult;
  // const { uid } = authResult;

Callers check: if (authResult instanceof NextResponse) return authResult; — no try/catch needed in the calling route.

TypeScript strict mode is on — ensure the return type is explicit and the function compiles without errors.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API routes | All 7 AI routes receive unauthenticated HTTP requests from the browser |
| Firebase Auth tokens | ID tokens are JWTs signed by Firebase; forgery requires Google's private key |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Spoofing | All 7 API routes (uid from body) | mitigate | requireAuth() verifies Firebase ID token via adminAuth.verifyIdToken(); uid derived server-side only |
| T-01-02 | Tampering | users/{uid}/jobs, users/{uid} Firestore docs | mitigate | After SEC-01, a caller cannot write to another user's Firestore path without holding their valid Firebase session token |
| T-01-03 | Information Disclosure | /api/settings/api-key GET — encrypted Anthropic key status | mitigate | requireAuth() on GET handler; no token = 401 before any Firestore read |
| T-01-04 | Elevation of Privilege | Anthropic API quota consumption via /api/fit-score et al | mitigate | callAI() fetches key by server-verified uid; attacker cannot bill a victim without their Firebase token |
| T-01-SC | Tampering | npm installs | accept | No new npm packages introduced in this plan; no install tasks |
</threat_model>
